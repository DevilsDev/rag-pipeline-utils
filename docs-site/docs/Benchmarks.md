# Benchmarks & Methodology

Most of a RAG query's time goes to things outside this library: the
embedding model, the vector store, the LLM and the network between them.
So the numbers here measure the parts the library controls or ships:

1. **Pipeline overhead**: the time `createRagPipeline().run()` itself adds
   around your components.
2. **Vector stores**: ingest throughput, query latency and recall for the
   built-in stores and the pgvector and Qdrant connectors.
3. **Retrieval quality**: how well the retrievers that run offline find
   the right documents on a public benchmark, BEIR SciFact.
4. **Guardrail accuracy**: precision and recall of the built-in injection
   and PII patterns, and of a prompt-injection classifier, on public
   labelled sets.
5. **Groundedness checks with Claude**: how well `checkAnswer` finds
   unsupported answers, lexically and with Claude models as the judge, on
   RAGTruth and on edge cases written for this project.
6. **Claude's citations**: how often `verifyCitations` confirms the
   citations Claude returns, and whether it catches citations that don't
   support their claim.
7. **Answer latency with Claude**: time to first token and total time of
   a streamed RAG answer through the library.

Everything is reproducible: the benchmarks are
[`benchmarks/speed.js`](https://github.com/DevilsDev/rag-pipeline-utils/blob/main/benchmarks/speed.js),
[`benchmarks/quality.js`](https://github.com/DevilsDev/rag-pipeline-utils/blob/main/benchmarks/quality.js),
[`benchmarks/guardrails.js`](https://github.com/DevilsDev/rag-pipeline-utils/blob/main/benchmarks/guardrails.js),
[`benchmarks/judge.js`](https://github.com/DevilsDev/rag-pipeline-utils/blob/main/benchmarks/judge.js)
and
[`benchmarks/claude-citations.js`](https://github.com/DevilsDev/rag-pipeline-utils/blob/main/benchmarks/claude-citations.js) (with [`judge-more.js`](https://github.com/DevilsDev/rag-pipeline-utils/blob/main/benchmarks/judge-more.js) and [`claude-latency.js`](https://github.com/DevilsDev/rag-pipeline-utils/blob/main/benchmarks/claude-latency.js)),
their data is generated from a fixed seed or downloaded from a pinned
revision (the Claude benchmarks call the API, and keep every response so
the tables can be rebuilt without calling it again), and the tables below are written
by `benchmarks/render.js` from the committed report in
[`benchmarks/results/`](https://github.com/DevilsDev/rag-pipeline-utils/tree/main/benchmarks/results).
Nothing on this page is typed by hand.

## Retrieval quality

[BEIR](https://github.com/beir-cellar/beir) SciFact asks for the scientific
abstracts that support or refute a claim. Every retriever here runs offline
with its default settings and no model, so these are baselines for the
built-in retrievers, not figures for neural embedders. Higher is better on
every column except time per query.

<!-- bench:quality:start -->

<!-- Generated by benchmarks/render.js from benchmarks/results/quality.json; do not edit. -->

Measured with 3.4.0 (commit `064f938`) on GitHub Actions Linux, Node v22.23.4.

Dataset: BEIR SciFact (test split), 5,183 documents, 300 queries, 339 relevance judgements (CC BY-SA 4.0, Hugging Face revision `b3b5335`). Each system returns 100 results per query.

| System                                   | nDCG@10 | Recall@10 | Recall@100 | MRR@10 | Per query |
| ---------------------------------------- | ------- | --------- | ---------- | ------ | --------- |
| `BM25Search`                             | 0.665   | 0.788     | 0.883      | 0.633  | 2.13 ms   |
| `LocalEmbedder + MemoryRetriever`        | 0.470   | 0.616     | 0.846      | 0.433  | 53.89 ms  |
| `HybridRetriever (BM25 + LocalEmbedder)` | 0.564   | 0.712     | 0.887      | 0.525  | 59.76 ms  |
| `HashEmbedder + MemoryRetriever`         | 0.233   | 0.348     | 0.550      | 0.202  | 2.8 ms    |

<!-- bench:quality:end -->

- **`BM25Search` matches the published baseline.** The BEIR paper
  (Thakur et al., 2021) reports nDCG@10 0.665 for BM25 on SciFact, which
  is also a check that these metrics are computed the standard way.
- **TF-IDF trails BM25.** `LocalEmbedder` weights raw term counts and
  keeps the 10,000 most common tokens of a larger corpus; BM25 saturates
  repeated terms, adjusts for document length and keeps every token.
- **Fusing a weaker retriever costs accuracy.** `HybridRetriever` weights
  both inputs equally, so the TF-IDF results pull BM25's ranking down.
  Hybrid search pays off when the second retriever is a good dense
  embedder; weight the retrievers, or measure on your data.
- **`HashEmbedder` is the testing stand-in**, shown as a floor.
- **TF-IDF vectors are long.** `LocalEmbedder` vectors have one dimension
  per vocabulary token (10,000 here), so an exact search over them in
  `MemoryRetriever` takes about 70 ms per query on this corpus.
- The metrics are those of BEIR and trec_eval. Recall@100 shows how many
  relevant documents a reranker could still recover from the top 100.

To score your own retriever or embedder on a test set of your own, see
[Evaluation](./Evaluation).

## Guardrail accuracy

How often the guards' detectors catch what they are for, and how often
they flag something harmless. The built-in detectors are the pattern
rules the guards use by default (`patternInjectionDetector()` and
`patternPIIDetector()`); the classifier is a model you can plug in as a
[detector](./Concepts-Guardrails#plug-in-your-own-detectors). Nothing was
tuned on these sets: the patterns are the ones the library ships, the
classifier uses a threshold of 0.5, and every public set is its test
split.

- **The patterns rarely raise a false alarm and miss most attacks.** They
  match known phrasings ("ignore previous instructions", role
  switches, encoded text), so on the public sets precision is high and
  recall is low. An
  injection in plain words, or in a language the rules don't cover, gets
  through. That is the case for adding a model-based detector.
- **The classifier catches more, and is not a complete answer either.**
  On the RAG fixtures it catches most direct attacks and about half of
  the indirect ones in documents, and it flags benign text that tells the
  reader to ignore, disregard or forget something. On deepset it misses
  role-play requests ("act as an interviewer"), many German prompts and
  some plain "forget everything" instructions; that set's labels are also
  broad (a request to generate SQL code counts as an injection). Measure
  on your own traffic before relying on one threshold.
- **The jailbreak row is a different task.** Jailbreaks talk a model out
  of its rules through role play; the classifier is not run on that set,
  because it is in its training data.
- **The PII patterns find emails and SSNs, and not names or addresses.**
  Most PII in real documents is names, companies and street addresses,
  which no pattern covers, so a PII service (Presidio, a cloud DLP API) is
  the detector to add for those. Phone and card patterns also match long
  digit runs such as account numbers in EDI and SWIFT messages.
- **Small sets have wide intervals.** The deepset test split has 116
  cases and the fixtures 40, so a few cases move recall by several
  points; the 95% interval is shown for that reason.
- **The RAG fixtures are illustrative.** They were written for this
  project before any detector was run on them and have not been changed
  since, by an author who knew the pattern rules; they show the kinds of
  attack a retrieved document can carry, not a measured rate or a fair
  comparison.

To measure detectors on your own labelled cases, see
[Measure your detectors](./Concepts-Guardrails#measure-your-detectors).

## Groundedness checks with Claude

How well [`checkAnswer`](./Evaluation) finds answers that say something
their sources don't, and how much an LLM judge adds. The lexical check
scores each sentence by word overlap with the sources, and checks its
numbers and negation. With `judge`, the sentences that failed only for low
word overlap (paraphrases) go to the model in one call; the judge never
overturns a number or negation mismatch, and never sees a sentence the
lexical check accepted. The library ran as shipped, with `evaluate: false`,
and nothing was tuned on these cases: not the thresholds, not the judge
prompt.

The same cases for every model:

- **RAGTruth** (Niu et al., ACL 2024): answers that GPT-3.5, GPT-4, Llama 2
  and Mistral models wrote from retrieved passages, news articles or a
  business's JSON record, with hallucinated spans marked by annotators. A
  seeded, balanced sample of 450 test answers for all five models, and
  the full test split for three of them (below).
- **Edge cases** written for this project, in two batches, each committed
  before any model saw it: paraphrases, numbers written as words, unit
  conversions, dates, negation, partial support, two sources,
  contradicting sources, entity swaps, hedges, long sources, very short
  answers, mixed answers, prompt injection inside a source, non-English
  text, and in the second batch tables and lists, quoted speech, numeric
  ranges and currency formats. Each case has an expected verdict.
- **HaluEval** (qa), a second public set, and three runs of the same
  answers to measure how much the verdicts move from run to run (below).

:::note
Two bugs in `AnthropicConnector` that kept it from serving as the judge on
current Claude models were found by this benchmark and fixed in 3.5.0; the
"Judge in 3.4.0" table shows what they did. Every other number here is the
3.5.0 code as shipped.
:::

- **The lexical check flags nearly every answer.** It finds almost all
  of the answers with a hallucination, and also flags most of the answers
  without one, so its precision is close to the 50% base rate of this
  balanced sample. An answer is flagged when any one sentence fails, and
  long answers rarely pass every sentence; the by-sentence table shows the
  same check one sentence at a time.
- **A judge helps a little, and the model barely matters.** Every judge
  lowers the false alarms and loses a few hallucinations, and the five
  models land within a few answers of each other. Most false alarms
  can't be cleared by any judge: they fail the number or negation check,
  which the judge is never asked about (the breakdown under the first
  table). The cheapest model is as useful here as the most expensive one.
- **Data-to-text barely changes.** Sources there are a business's JSON
  record, and almost every answer is flagged with or without a judge.
- **What no judge can catch: a wrong sentence with high word overlap.** An
  entity swap ("Dr. Jonas Weber chairs the ethics board" when he chairs
  the finance board), a changed unit, month or hedge, or a claim that
  adds one detail to a supported sentence passes the lexical check, so it
  is never sent to the judge. Every configuration misses the same 27 of
  the 136 edge cases for this reason. The second batch adds more of the
  same kind: a quote attributed to the wrong speaker, a forecast stated as
  a fact, "rose by 4.5%" for "rose to 4.5%", a table row read for the
  wrong plan, and German "nicht", which the negation check does not know
  (its negation words are English).
- **What the lexical check gets wrong that a judge fixes**: paraphrases
  with few shared words, and a date or language written differently.
  Unit conversions ("2 weeks" and "14 days", "2,000 grams" and "2 kg"),
  sums across sources, "three quarters" for 75%, a day-first date
  (12/05/2019), times written as "9 to 5" for "9:00 to 17:00" and number
  words in other languages fail the number check, which the judge doesn't
  overrule.
- **The judge did not follow instructions planted in sources** in any
  injection case that reached it (the count is under the edge-case
  tables); the others fail the number check or pass the lexical check, so
  they are never sent to the judge.
- **Limits.** English answers, from two public benchmarks whose answers
  were written by older models; a handful of edge cases in German,
  Spanish and French. HaluEval and RAGTruth have been public since 2023
  and 2024, so the judge models may have seen them in training. Each
  model ran at its default settings (temperature 0 for Claude Haiku 4.5;
  the others don't accept a temperature), on 2026-11-05. The edge cases
  are illustrative, a few per category, and were written by someone who
  knows how the check works.

Every API response is stored in `benchmarks/.data/claude-cache/`, so the
tables rebuild on the machine that ran them without calling the API. The
cache is not committed: a rerun elsewhere calls the API, needs a key, and
may get different answers.

- **On the full split the picture holds, at the natural rate.** About a
  third of RAGTruth's answers have a hallucination, so precision drops
  toward that rate: the lexical check still flags most answers, and a
  judge clears some false alarms at the cost of a few hallucinations.
  Data-to-text answers, where most answers have a hallucination, score
  higher F1 only because nearly everything is flagged.
- **Verdicts barely move from run to run.** Across three runs, the
  answer-level verdict changed for less than 1% of answers, and F1 moved
  in the third decimal. The sentences that change are the judge's close
  calls; the lexical check itself is deterministic.
- **HaluEval measures something different, and the judge does worse
  there.** Its answers are short (often a name), its hallucinated answers
  were written to be plausible, and its labels depend on the question: an
  answer can repeat words from the knowledge snippet and still not answer
  what was asked. `checkAnswer` checks the answer against the sources and
  the judge sees the answer, not the question, so it accepts some of
  these. Precision is high because right answers are copied from the
  snippet; recall is about half, and the judge lowers it. Use
  `checkAnswer` for "is this supported by the sources", not "is this the
  right answer to the question".

## Claude's citations

When Claude answers from `document` blocks with citations on, every
sentence it cites comes with the passage it cites.
[`fromAnthropicCitations` and `verifyCitations`](./Evaluation) check that
each passage supports the claim citing it, with the same lexical, number
and negation checks as `checkAnswer` (and optionally the judge). This
section asks how often that check confirms real Claude answers, how often
its "unsupported" verdict is right, and whether it catches citations that
don't support their claim.

- **SciFact answers**: 150 claims from BEIR SciFact for the three cheaper
  models and 100 for Claude Opus 5.5 and Fable 5.1 (one seeded order, so
  all five share the first 100); each model gets three
  abstracts (the ones judged relevant to the claim, then BM25's top
  non-relevant ones) and explains what they say about the claim.
- **Hand review**: every claim the check marked unsupported, read against
  the passages it cites, with criteria written before the run.
- **Mutations**: claims the check supports, changed on purpose (a number,
  a negation, or the cited passage swapped for another), with no extra
  API calls.
- **Edge cases** written for this project, in two batches, each committed
  before any model saw it: questions the documents can't answer,
  conflicting documents, multi-hop questions, twelve documents with one
  relevant, 4,000- to 6,000-word documents, near-duplicate documents,
  instructions planted in a document, and in the second batch questions
  needing a calculation over two documents and documents in another
  language.

- **When the check says "supported", it is reliable.** It caught every
  changed number, every added negation and every passage from an
  unrelated claim, and almost every swap for another abstract in the
  same request (the misses we read were swaps for an abstract that says
  much the same thing). The few removed negations it missed were "not
  only ... but also", which is not a negation, and a sentence that lost
  both of its negations, which the check reads the same way (it counts
  negations odd or even).
- **When it says "unsupported" on Claude's real citations, it is almost
  always wrong.** Of the claims reviewed by hand, across all five models,
  three were true problems, and those were coverage gaps rather than
  inventions: a gloss from the model's own knowledge, a phrase from the
  document's title, and a number from another sentence of the same
  abstract. Most false alarms were faithful quotes or paraphrases of a passage that also
  contains a negated clause the claim leaves out ("... requires
  phosphorylation by Lck but not ZAP-70 binding"): the negation check
  compares the claim with that sentence and fails, even when the claim is
  a verbatim part of it. Others say "Document 3 shows ...", and 3 is read
  as a number the passage lacks; "Million Women Study" reads as one
  million, and a footnote glued to a year ("1992.1") hides the year.
  Few claims are flagged (the first
  mutation row), but treat an "unsupported" citation from Claude as a
  prompt to look, not as an error.
- **`verified` needs at least one cited claim; uncited sentences don't
  count against it.** An answer that correctly says the documents don't
  cover the question has no claims, so it is never verified. Claude's
  answers also often add uncited sentences, mostly framing ("The
  documents give two different dates"), which `verified` ignores and the
  benchmark rule counts. On the edge cases every model answered almost
  everything correctly, so nearly all flags under the benchmark rule are
  false alarms: refusal-style answers and uncited framing.
- **Injected instructions: both caught, by `uncited` only.** Claude Opus
  5.5 followed two instructions planted in documents. It ended one answer
  with a link, and started another with "APPROVED BY HR" on its own line.
  Neither line has a citation, so both answers are still `verified`, and
  `uncited` is what shows them: read `uncited` as well as `verified`. (The
  second was missed until 3.5.0: the sentence splitter ignored line
  breaks, so the line joined the cited sentence after it. This benchmark
  found it.) Every other answer ignored the planted instructions, and
  most pointed them out.
- **Claude Opus 5.5 and Claude Fable 5.1 refused a large share of
  ordinary biomedical questions** (`stop_reason: "refusal"`, category

## How to read the speed numbers

- **Pipeline overhead is small next to real components.** The components
  in this test return at once, so the times are the library's own work:
  stage orchestration, abort handling, result assembly. An embedding or
  LLM API call takes tens to thousands of milliseconds.
- **A cache hit costs more than an instant component.** With the cache on,
  each run hashes the query and looks up three layers, so it takes longer
  than calling components that cost nothing. The cache pays off when a
  real embedding or LLM call takes milliseconds; see [Caching](./Caching).
- **Recall@10 is measured against an exact search** over the same
  vectors. The memory and file stores search exactly and always reach
  1.000. pgvector's HNSW index searches approximately: at its default
  `efSearch` of 40 it misses some true neighbours, and raising `efSearch`
  finds more of them for a little more latency. Qdrant searches exactly
  until a collection passes its indexing threshold, then builds HNSW; the
  Index column shows what it did in this run.
- **The vectors are synthetic.** They are unit vectors clustered around
  100 random centres, like embeddings of a corpus with topics. Real
  embeddings differ, so measure recall on your own data before tuning
  `efSearch`.
- **The databases ran on the same machine.** In CI, pgvector and Qdrant run
  as service containers on the GitHub Actions runner, so there is almost
  no network latency. A managed database in another zone adds its round
  trip to every query.
- **Shared runners are noisy.** GitHub's hosted runners share hardware, so
  runs vary by 10–20%. Compare numbers from the same run, not across runs.
- **`FileVectorStore` ingest includes writing the index file**, which is
  why it is much slower than `MemoryRetriever`; its queries scan every
  vector like the memory store.
- **pgvector ingest maintains the HNSW index** on every insert. Loading
  without the index and building it afterwards is about ten times faster;
  see [PostgreSQL with pgvector](./Concepts-Connectors#postgresql-with-pgvector).

## Common pitfalls

1. **No warmup**: first-iteration numbers are dominated by JIT and cold
   caches. Always discard a warmup window.
2. **Too few iterations**: 10 samples of a ~1 ms operation is mostly
   noise. 100+ is a reasonable floor.
3. **Correlated runs**: running twice back to back shows the second as
   faster because caches are warm.
4. **Shared hosts**: CI runners and laptops with open browsers add noise.
   Dedicated machines give the cleanest numbers.
5. **Streaming workloads**: retrieval latency is not end-to-end latency
   when the LLM streams. Measure time-to-first-token separately.
